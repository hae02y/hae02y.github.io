Util, Constant 클래스​

  1. 두 개 이상의 클래스에서 동일한 기능을 필요로 하면 Util, Constant 클래스로 나눕니다.

    1. 각각의 서비스 클래스에서 Authentication 에 있는 정보를 조회하는 기능이 필요하다면?

      • SecurityUtil 클래스에서 해당 기능 일임
      public class SecurityUtil {

          public static Long getCurrentId() {
              final Authentication authentication = SecurityContextHolder.getContext().getAuthentication();

              CustomUserDetails userDetails = (CustomUserDetails) authentication.getPrincipal();

              validate(authentication);

              return userDetails.getId();
          }

          private static void validate(Authentication authentication) {
              if (authentication == null || authentication.getName() == null) {
                  throw new MemberNotFoundException();
              }
          }
      }

    2. 특정 상수가 계속해서 반복된다면?

      • Constant 클래스 선언해서 사용
      public class AuthConstant {

          public static final String AUTHORIZATION = "Authorization";
          public static final String BEARER = "Bearer ";
          public static final String REFRESH = "Refresh";
          public static final String Auth_PATH = "/v1/api/auth";
          public static final String LOGIN_PATH = "/v1/api/auth/login";
          public static final String REFRESH_URL = "/v1/api/auth/refresh";

          public static final String AUTHORITIES_KEY = "auth";

          ....
      }
      • 장점 : 상수값 변경 시 한번에 적용 가능
      • 문제점 : OCP 문제, 상수 사용하는 클래스는 모두 의존성이 높아짐

exception​

  1. 기존 방식
    • 기존 예외 처리 방식 : 예외 상황에 대한 ExceptionCode 작성 후 BusinessLogicException 의 파라미터로 넣어서 사용
  • 문제점
    • 의존성 자석 문제 → 무분별한 Enum import
    • OCP 위반 → 오류를 추가하려면 기존 클래스를 수정해야 함
  1. 수정 방식
  • Business 예외의 최상위 추상 클래스 : BusinessException
  • 각 도메인 및 상황에 맞는 추상 자식 클래스 (ex. MemberException)
  • 도메인별 상황에 대한 구체적인 클래스 선언
@Getter
public abstract class BusinessException extends RuntimeException {

    private final String errorCode;
    private final HttpStatus httpStatus;

    protected ApplicationException(String errorCode, HttpStatus httpStatus, String message) {
        super(message);
        this.errorCode = errorCode;
        this.httpStatus = httpStatus;
    }
}
--------------------------------------------------------------------------------------------------------------
public abstract class MemberException extends BusinessException {
    protected MemberException(String errorCode, HttpStatus httpStatus, String message) {
        super(errorCode, httpStatus, message);
    }
}

@Getter
public class MemberNotFoundException extends MemberException{

    public static final String ERROR_CODE = "MEMBER-401";

    public MemberNotFoundException() {

4. 테스트​

  • 모든 클래스, 메서드에 대한 단위 테스트 진행
  • 예외 상황이 있다면 반드시 예외가 터지는지 테스트
  • 테스트는 되도록 Edge case 로 테스트 → Edge case 란 경계선에 있는 값을 테스트
    • 예를 들어 Member 의 name 이 1~10글자라면
      • happy case 로 10글자로 테스트
      • 예외 케이스로 11글자 테스트 → 예외가 터지는지 확인
  • 테스트도 문서다 → 읽기 편하고, 어떤 테스트인지 한 눈에 알 수 있어야 함
    • @DisplayName 을 활용하여 테스트의 조건, 결과를 서술
      • @DisplayName("member 의 이름과 패스워드로 멤버를 생성한다.")
      • @DisplayName("member 의 이름이 중복되면 MemberNameDuplicateException 예외가 발생한다.")
    • BDD 사용 → given, when, then

Lombok 사용 및 getter, setter​

  • @Getter 는 필요한 곳에 사용

  • @Setter 는 사용 지양 → 필드 값 변경이 필요하면 비즈니스 로직을 생성

    • 변경하면 안되는 값도 변경을 시도하려고 할 수 있기 때문 → 캡슐화
    class Member {
    	private Long id;
    	private String name;
    	private String password;

    	public changeName(String name){
    		//이름을 변경하는 로직
    	}
    }

  • @~~ArgsConstructor 는 필요할 때만 사용 → 필요한 생성자만 만들어놓고 private 으로 막음

    • 객체 생성은 create~ 나 of 등 static 클래스 사용 → 비즈니스 로직을 거치지 않은 무분별한 생성 방지
    @AllArgsConstructor(access=PRIVATE)
    class Member {
    	private Long id;
    	private String name;
    	private String password;

    		this.name = name;
    		this.password = password;
    	}

    	}
    }
